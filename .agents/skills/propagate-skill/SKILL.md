# Propagate Skill Changes

Build one canonical repository-neutral contract from the requested change and every applicable
consumer, keep repository-specific rule guidance in each target's `project.md`, and distribute all
useful generic skills and applicable generic rules.

## Dependencies

- `coordinate-repositories` — coordinate the generic multi-repository work this skill delegates.
- `code-simplify` — equip every propagated repository for mandatory implementation simplification.

## Skill Listing

When the invocation names no skill or rule other than `propagate-skill` as the workflow trigger,
list every canonical skill found at `.agents/skills/*/SKILL.md` as an alphabetized Markdown bullet
list, then stop. Do not discover repositories or mutate files for a listing-only invocation.

## Workflow

1. Identify every skill or rule created, updated, or explicitly invoked in the same user message, excluding `propagate-skill` itself only when it is the workflow trigger rather than an artifact to propagate. Resolve skill sources at `.agents/skills/<name>/SKILL.md` and rule sources at `.agents/rules/<name>.md`. Repository skill directories must never contain `agents/openai.yaml`; remove that file from canonical and consumer artifacts instead of creating, copying, or validating it. Read every canonical skill directory completely and classify it by semantics rather than name. Before calling an artifact repository-neutral, scan every instruction, example, path, package name, service name, organization name, URL, provider/model assumption, and supporting file for product or repository coupling. A generic-looking name or description never outweighs branded content such as a product namespace, proprietary package, fixed service topology, repository-owned path, or product-specific workflow. Record the exact evidence used for each classification.
   - Broadly useful repository-neutral workflow skills apply to every repository only when their complete contents are repository-neutral.
   - Repository-neutral language, framework, provider, or workflow skills apply when the target's remote default branch proves the prerequisite.
   - Product-specific skills remain within the matching product boundary and must never be used as a canonical generic source. A hard-coded product identifier or proprietary path is conclusive local-only evidence unless the user explicitly approves a generic rewrite after seeing the exact wording.
   - A rule that references repository-owned skills, directories, branch or pull-request lifecycle conventions, or another local workflow is repository-specific unless the same complete contract is proven to exist in every intended consumer. Keep it in each matching repository's `project.md`; never place it in a shared rule merely because the prose omits a product name.
   - Ambiguous artifacts remain excluded until the user sees the exact coupling evidence and chooses whether to keep them local, rewrite them generically, or propagate them to an explicitly bounded product family.

   Before treating an included skill directory as repository-owned canonical content, search
   [skills.sh](https://skills.sh/) for the same skill name and compare the complete semantics and
   supporting files. When the local skill is the same or substantially the same as a published
   skill, use the skills.sh source repository and upstream slug in `.agents/skills.json` and
   remove the manually maintained local definition. Set `update_on_sync` to `true` for sources
   owned by companies or organizations and to `false` for sources owned by personal accounts.
   Keep `petergyang/no-ai-slop` enabled as the explicit personal-account exception. Verify source
   ownership and ask the user when it is ambiguous. The published skill wins wholesale: do not
   retain local additions, wording changes, or supporting files as a fork. Ask the user before
   choosing between plausible upstream identities or classifying a similar local skill as
   meaningfully distinct. Let Agent Sync vendor the registered upstream artifact; do not copy the
   deleted local definition between repositories.

   Include every broadly useful repository-neutral skill in the propagation set even when the user did not name it, and always include `code-simplify`. For every included skill, read its declared `## Dependencies` section, add each dependency, and repeat recursively until the graph is complete. Deduplicate dependencies and report cycles. Inventory the canonical `.agents/rules/*.md` files as candidate companion artifacts; every non-project rule that applies to a target's stack, tooling, or workflow belongs in that target even when the user named only skills. Never copy `project.md` between repositories.
2. Determine whether the workspace is on the user's local computer or in a cloud or ephemeral environment. Use filesystem layout, repository remotes, environment markers, and accessible sibling repositories as evidence. If the environment is cloud or remains ambiguous, do not search broadly or mutate other repositories; report the limitation or ask the user.
3. On a local computer, find the repository collection containing the current repository by inspecting its parent directories and nearby Git worktrees. Search bounded repository roots first; do not crawl the entire home directory when the collection root is discoverable. Discover candidate Git repositories independently of agent-system files: never require `.agents`, `AGENTS.md`, an Agent Sync workflow, or provider mirrors for a repository to enter the candidate set. Resolve each candidate's normalized remote repository identity and deduplicate multiple checkouts or worktrees of the same remote. Freeze the resulting target manifest before editing. For every normalized remote, record the expected canonical artifacts, external-skill registry entries, required workflow behavior, explicitly forbidden artifacts, pull-request identity, and current state. Track each row through `pending`, `changed`, `pushed`, and `remote-verified`, or a terminal `skipped` or `blocked` state with a concrete reason.
4. Fetch each candidate remote and inspect its current remote default branch before assessing it. Never use the local checkout's current branch, working tree, or stale remote-tracking state to decide whether the repository has the agent system or whether an artifact applies. Establish the in-scope target repositories from the bounded collection and the user's request. Assess every selected skill, recursively selected dependency, explicitly selected rule, and canonical companion rule independently for applicability to every candidate target, using the remote default branch's languages, frameworks, tooling, and workflow; existing agent configuration is evidence about current state, not an applicability prerequisite. Do not use predefined skill-to-repository mappings.
   - Assess compliance separately from applicability. A repository that currently violates an applicable rule is still a positive target; never classify a rule as inapplicable merely because adopting it requires repository changes.
   - For every apparent incompatibility, determine whether it is target noncompliance, a genuinely inapplicable rule, or an intentional repository contract that conflicts with the canonical rule. Cite concrete files and behavior rather than inferring intent from the current implementation.
   - Estimate how feasible it is to bring the repository into compliance: identify the affected files and public/runtime/CI contracts, the likely change size and risk, and the validation needed. Give the user a recommendation for a separate focused follow-up. Propagation never remediates application or package source.
   - When an applicable target already has the agent system, add or update every included generic skill and applicable canonical rule. Register external skills in `.agents/skills.json` with the verified skills.sh repository and upstream slug; do not propagate a manually maintained directory for the same skill. Copy each repository-owned generic skill directory and every non-project rule byte-for-byte from the canonical source; never rewrite them for the target. Keep `project.md` repository-owned.
   - When an applicable target lacks the agent system, bootstrap it in the same propagation pull request. This is required: a missing Agent Sync system is never a reason to skip an otherwise applicable repository. Create the canonical `.agents` source layout, add the selected skills, their dependencies, and every applicable canonical rule, add the canonical external-skill registry when the synchronization action expects one, and add the minimum Agent Sync implementation, runtime-version file, and workflow required to synchronize that repository. Derive synchronization files from the current canonical agent-enabled repository. If target workflow requirements conflict with the canonical setup, ask the user before adapting it. Do not copy unrelated project rules or skills merely to populate the new layout.
   - Never create or edit provider mirrors such as `.codex`, `.claude`, or `.cursor`; the bootstrapped synchronization workflow owns their generation.
5. Before comparing, read the complete originating file and the complete existing target file (when present), plus the target's complete `project.md` and enough nearby guidance to understand local context. Never infer that files are identical from matching names, prior propagation, hashes, or a partial diff. Compare full text, line counts, and an exact diff before deciding whether a target is current. Then classify every difference before changing it:
   - **Requested semantic delta** — behavior the user explicitly requested in this propagation. Propagate it unchanged where it is compatible. If target evidence makes any part incompatible or repository-specific, stop and ask the user whether to change the canonical artifact, exclude the target, or accept another explicit resolution; never rewrite the delta automatically.
   - **Reusable consumer guidance** — repository-neutral behavior found in an applicable consumer but absent from the origin. Present it to the user as a candidate canonical change and wait for approval before merging it into the origin or propagating it.
   - **Stale generic guidance** — target wording proven to be an older revision of the same repository-neutral guidance by an exact newer contract and unambiguous history or explicit user intent showing that the newer wording supersedes it. Replace it only when that evidence establishes the disposition of the complete older wording. A newer origin date, commit, hash, or omission from the origin is never proof that consumer wording is stale, conflicting, or safe to delete.
   - **Target noncompliance** — the canonical artifact applies, but current target code, configuration, tests, or workflow violates it. Do not weaken or tailor the artifact. Present the violation and feasibility assessment, recommend whether to fix it in the propagation PR or a follow-up, and ask the user to choose before changing repository behavior.
   - **Conflicting generic guidance** — repository-neutral contracts that cannot both remain as written. Present the conflicting text, affected repositories, and concrete resolution choices to the user; do not edit either side before the user chooses.
   - **Target-specific guidance** — behavior justified by the target's own tools, product, paths, architecture, or workflow. Repository-specific rule guidance belongs only in that target's `project.md`; never retain it in another rule file or create a branded rule file. Move it without semantic loss only after its ledger disposition is authorized. Product-specific skills may remain local. If local guidance conflicts with a generic artifact, stop and ask the user how to resolve the semantics before moving or rewriting either side.

   Every non-project rule and every included generic skill directory must remain byte-identical to the canonical source. `project.md` and product-specific skills remain repository-owned.
6. Build a semantic deletion ledger before editing any existing consumer artifact. Record every complete sentence, bullet, paragraph, example, or contract that the proposed result would remove, narrow, or materially weaken. Each entry must include the repository and artifact, exact existing wording, classification from step 5, evidence for that classification, and proposed disposition: retain, generalize into the canonical source, replace, or delete.
   - Treat compatible repository-neutral guidance as an additive candidate canonical change. Preserve it unchanged until the user explicitly approves its generalization or another disposition.
   - Absence from the originating artifact is never deletion authority. Broad requests to propagate, synchronize, converge, use the canonical version, or use the same language do not authorize removal or weakening of consumer guidance.
   - A ledger entry may be replaced or deleted only when the exact current request explicitly removes it, an exact newer contract demonstrably supersedes the complete wording, or the wording is part of a true conflict and the user explicitly chooses the retained contract.
   - Present the complete ledger to the user, not representative samples or an abbreviated summary. Do not avoid a generic conflict by labeling one side project-specific. Do not edit artifacts while any proposed deletion or weakening lacks an explicit disposition.
7. Present every incompatibility, target violation, feasibility assessment, recommendation, proposed canonical generalization, and semantic deletion ledger entry to the user before editing canonical guidance. Target noncompliance is report-only in this workflow: recommend a separate focused follow-up, but never edit application code, package source, dependency manifests, tests, runtime configuration, or other repository behavior to satisfy a propagated rule. Offer concrete choices for artifact conflicts: defer remediation, exclude a genuinely inapplicable rule, retain compatible consumer wording, generalize it into the canonical source, or change the canonical rule. Apply only the artifact resolution the user selects, then propagate the resulting canonical artifacts to every applicable target.
8. Finalize and validate the originating canonical artifacts after all incompatibilities are resolved and before distributing them.
9. For changes limited to `.agents` skills or rules, validate the Markdown, confirm no repository skill contains `agents/openai.yaml`, and run `git diff --check`; do not run unit, integration, typecheck, lint, build, agent-sync, or source-to-mirror tests because no repository has tests for skill content. For a newly bootstrapped agent system, also validate the synchronization workflow and registry syntax without generating provider mirrors. Do not hand-edit provider mirrors; repository CI owns their generation. Compare the finalized result against every target's fetched remote default branch and fail validation if any sentence, bullet, paragraph, example, or contract was removed, narrowed, or materially weakened without an explicitly authorized deletion-ledger disposition.
   - When the user confines or removes a policy by concept, search the complete diff of every rule and skill for the heading, terminology, referenced artifacts, and semantic equivalents of that policy. Fail validation if it remains outside the authorized repository or artifact boundary; checking only the originally named file is insufficient.
   - Immediately before committing and again before pushing, fetch the remote default branch and rebuild the applicability record for every skill directory and every entry in `.agents/skills.json` in the proposed result, not only artifacts changed in the current pass. Require concrete evidence from that freshly fetched tree for every language-, framework-, provider-, or workflow-specific prerequisite. A feature branch, merge base, local checkout, prior commit, deleted artifact, existing registry entry, or earlier applicability result is not current evidence. Fail validation when any final skill lacks current applicability evidence; remove it only when the user has authorized that deletion, otherwise present it for a decision.
   - After pushing, read the remote pull-request head and repeat the complete registry and skill-set check against the latest remote default branch. Do not report success from local validation alone.
10. For cross-repository coordination, follow `coordinate-repositories` for bounded discovery, isolated-worktree safety, validation, and pull-request state handling. When the user authorizes persistent propagation, carry only canonical `.agents` artifacts and, when bootstrapping a missing agent system, the minimum agent-synchronization implementation, registry, runtime-version, or workflow files it requires. Exclude application code, package source, dependency manifests, tests, runtime configuration, provider outputs, unrelated in-progress work, and manually copied mirrors. Before deciding to reuse an existing pull request, query its current state: a merged pull request is treated as no pull request, so create a new branch and focused pull request. Reuse only an open pull request for the same active branch and task scope. Title the pull request as a synchronization of agent files (for example, `chore: sync agent files`); do not frame consumer changes as modernizing or changing the synchronization system.
11. After all changed rows are pushed, give an independent validation sub-agent the frozen manifest and exact expected and forbidden postconditions. The validator must query every current remote pull-request head, or the remote default branch when no open pull request exists, and audit complete canonical skill directories, `.agents/skills.json`, Agent Sync workflow behavior, and requested removals. It must return every mismatched row, not samples. Reconcile each mismatch and repeat the independent remote audit until every row is `remote-verified`, `skipped`, or `blocked`. If a validation sub-agent is unavailable, perform the same complete remote audit in a separate pass after discarding local assumptions.
12. Report the repositories updated, skipped, or blocked; the requested delta applied; target violations, feasibility judgments, recommendations, user-selected resolutions, and authorized semantic deletions; validation results; and every created pull-request link. Never report propagation as complete while any manifest row remains `pending`, `changed`, `pushed`, or otherwise unverified.

## Guardrails

- Preserve dirty worktrees and unrelated changes.
- When the user explicitly removes a canonical or consumer agent artifact, delete it directly and
  rely on Git history for recovery. Do not retain a Trash copy, backup directory, or temporary
  recoverable duplicate.
- Never change application code, package source, dependency manifests, tests, runtime configuration, or repository behavior during propagation. Report noncompliance and recommend a separate focused follow-up instead.
- Never reuse, alter, or clean a non-default working branch to perform propagation. Keep the original checkout intact and isolate the carry-over of canonical agent-system work.
- Treat the fetched remote default branch as authoritative for discovery and applicability; a stale or non-default local checkout must never exclude a repository.
- Never exclude a repository from discovery or applicability merely because it has no `.agents` directory or Agent Sync workflow; bootstrap applicable repositories instead.
- Every applicable repository must leave the propagation with a working Agent Sync system; add the minimum canonical bootstrap when it did not already have one.
- Create every broadly useful repository-neutral skill, explicitly selected skill, and recursively selected dependency when it is missing. Always add `code-simplify`. Add every canonical non-project rule whose behavior applies to the target; do not add inapplicable domain or framework guidance.
- Keep every propagated non-project rule and generic skill directory byte-identical to the canonical source. Never tailor them per repository. Keep repository-specific rule guidance only in `project.md`.
- Never resolve incompatible canonical, consumer, or target-specific guidance without presenting it to the user and receiving an explicit choice.
- Make canonical convergence additive by default. Never obtain byte identity by deleting compatible consumer guidance, and never interpret silence, omission, or a broad synchronization request as deletion approval.
- Do not remove, narrow, or materially weaken an existing semantic block unless its complete wording appears in the semantic deletion ledger with an explicit authorized disposition.
- Never treat existing repository noncompliance as evidence that an applicable rule should be tailored or omitted; surface the violation and remediation feasibility to the user.
- Author and replicate canonical `.agents` artifacts; provider-specific outputs must be generated only by the repository synchronization system when it is in scope.
- Never create, retain, or propagate `agents/openai.yaml` inside a repository skill directory.
- Treat locally generated provider outputs as disposable test artifacts and leave their publication to CI.
- Keep replicated code examples and reusable instructions repository-neutral; retain domain-specific material only where it is relevant to that target.
- Never propagate an artifact whose complete contents name a product, organization, proprietary package, fixed product topology, or repository-owned path beyond repositories that share that exact boundary. Treat a generic title as no evidence of generic applicability.
- Replace known older generic guidance with its newer canonical wording only when no incompatibility exists.
- Canonical convergence remains the goal, but user approval is required before incorporating consumer guidance or resolving conflicting contracts.
- Do not turn textual similarity or difference into authority; surface semantic incompatibilities for the user to resolve.
- Never propagate secrets, absolute machine paths, generated mirrors, or repository-specific operational details to unrelated repositories.
- Interruption, context compaction, tool failure, or partial success never removes a repository from the frozen target manifest. Resume from the first nonterminal row and rerun the complete remote audit before completion.
