# Propagate Skill Changes

Build one canonical repository-neutral contract from the requested change and every applicable
consumer, then propagate that contract without overwriting repository-specific guidance.

## Dependencies

- `coordinate-repositories` — coordinate the generic multi-repository work this skill delegates.

## Skill Listing

When the invocation names no skill or rule other than `propagate-skill` as the workflow trigger,
list every canonical skill found at `.agents/skills/*/SKILL.md` as an alphabetized Markdown bullet
list, then stop. Do not discover repositories or mutate files for a listing-only invocation.

## Workflow

1. Identify every skill or rule created, updated, or explicitly invoked in the same user message, excluding `propagate-skill` itself only when it is the workflow trigger rather than an artifact to propagate. Resolve skill sources at `.agents/skills/<name>/SKILL.md` and rule sources at `.agents/rules/<name>.md`. For every selected skill, read its declared `## Dependencies` section, add each named skill dependency to the artifact set, and repeat recursively until the dependency graph is complete. Deduplicate dependencies and report cycles rather than recursing indefinitely. Propagate dependencies even when the user named only the parent skill. Inventory the canonical `.agents/rules/*.md` files as candidate companion artifacts; every rule that applies to a target's stack, tooling, or workflow belongs in that target even when the user named only skills.
2. Determine whether the workspace is on the user's local computer or in a cloud or ephemeral environment. Use filesystem layout, repository remotes, environment markers, and accessible sibling repositories as evidence. If the environment is cloud or remains ambiguous, do not search broadly or mutate other repositories; report the limitation or ask the user.
3. On a local computer, find the repository collection containing the current repository by inspecting its parent directories and nearby Git worktrees. Search bounded repository roots first; do not crawl the entire home directory when the collection root is discoverable. Discover candidate Git repositories independently of agent-system files: never require `.agents`, `AGENTS.md`, an Agent Sync workflow, or provider mirrors for a repository to enter the candidate set. Resolve each candidate's normalized remote repository identity and deduplicate multiple checkouts or worktrees of the same remote.
4. Fetch each candidate remote and inspect its current remote default branch before assessing it. Never use the local checkout's current branch, working tree, or stale remote-tracking state to decide whether the repository has the agent system or whether an artifact applies. Establish the in-scope target repositories from the bounded collection and the user's request. Assess every selected skill, recursively selected dependency, explicitly selected rule, and canonical companion rule independently for applicability to every candidate target, using the remote default branch's languages, frameworks, tooling, and workflow; existing agent configuration is evidence about current state, not an applicability prerequisite. Do not use predefined skill-to-repository mappings.
   - Assess compliance separately from applicability. A repository that currently violates an applicable rule is still a positive target; never classify a rule as inapplicable merely because adopting it requires repository changes.
   - For every apparent incompatibility, determine whether it is target noncompliance, a genuinely inapplicable rule, or an intentional repository contract that conflicts with the canonical rule. Cite concrete files and behavior rather than inferring intent from the current implementation.
   - Estimate how feasible it is to bring the repository into compliance: identify the affected files and public/runtime/CI contracts, the likely change size and risk, and the validation needed. Give the user a recommendation for a separate focused follow-up. Propagation never remediates application or package source.
   - When an applicable target already has the agent system, update its existing selected skill paths and add or update every applicable canonical rule. Copy rules byte-for-byte from the canonical source; never rewrite a rule for the target.
   - When an applicable target lacks the agent system, bootstrap it in the same propagation pull request. This is required: a missing Agent Sync system is never a reason to skip an otherwise applicable repository. Create the canonical `.agents` source layout, add the selected skills, their dependencies, and every applicable canonical rule, add the canonical external-skill registry when the synchronization action expects one, and add the minimum Agent Sync implementation, runtime-version file, and workflow required to synchronize that repository. Derive synchronization files from the current canonical agent-enabled repository. If target workflow requirements conflict with the canonical setup, ask the user before adapting it. Do not copy unrelated project rules or skills merely to populate the new layout.
   - Never create or edit provider mirrors such as `.codex`, `.claude`, or `.cursor`; the bootstrapped synchronization workflow owns their generation.
5. Before comparing, read the complete originating file and the complete existing target file (when present), plus enough nearby target guidance to understand its repository-specific context. Never infer that files are identical from matching names, prior propagation, hashes, or a partial diff. Compare full text, line counts, and an exact diff before deciding whether a target is current. Then classify every difference before changing it:
   - **Requested semantic delta** — behavior the user explicitly requested in this propagation. Propagate it unchanged where it is compatible. If target evidence makes any part incompatible or repository-specific, stop and ask the user whether to change the canonical artifact, exclude the target, or accept another explicit resolution; never rewrite the delta automatically.
   - **Reusable consumer guidance** — repository-neutral behavior found in an applicable consumer but absent from the origin. Present it to the user as a candidate canonical change and wait for approval before merging it into the origin or propagating it.
   - **Stale generic guidance** — target wording known to be an older revision of the same repository-neutral guidance now present in the origin, based on repository history, a prior propagation, or another unambiguous superseding contract. Replace it with the newer originating wording. Never preserve or report stale generic wording as candidate conflicting or target-specific guidance merely because it differs from the current requested delta.
   - **Target noncompliance** — the canonical artifact applies, but current target code, configuration, tests, or workflow violates it. Do not weaken or tailor the artifact. Present the violation and feasibility assessment, recommend whether to fix it in the propagation PR or a follow-up, and ask the user to choose before changing repository behavior.
   - **Conflicting generic guidance** — repository-neutral contracts that cannot both remain as written. Present the conflicting text, affected repositories, and concrete resolution choices to the user; do not edit either side before the user chooses.
   - **Target-specific guidance** — behavior justified by the target's own tools, product, or workflow. Preserve unrelated target-specific artifacts. If it conflicts with a selected canonical artifact or prevents exact rule synchronization, stop and ask the user how to resolve it.

   Rules must remain byte-identical to the canonical source. Skills may retain approved target-specific additions only after the user resolves the variance explicitly.
6. Present every incompatibility, target violation, feasibility assessment, recommendation, and proposed canonical generalization to the user before editing canonical guidance. Target noncompliance is report-only in this workflow: recommend a separate focused follow-up, but never edit application code, package source, dependency manifests, tests, runtime configuration, or other repository behavior to satisfy a propagated rule. Offer concrete choices for artifact conflicts: defer remediation, exclude a genuinely inapplicable rule, or change the canonical rule. Apply only the artifact resolution the user selects, then propagate the resulting canonical artifacts to every applicable target.
7. Finalize and validate the originating canonical artifacts after all incompatibilities are resolved and before distributing them.
8. For changes limited to `.agents` skills or rules, validate the Markdown and run `git diff --check`; do not run unit, integration, typecheck, lint, build, agent-sync, or source-to-mirror tests because no repository has tests for skill content. For a newly bootstrapped agent system, also validate the synchronization workflow and registry syntax without generating provider mirrors. Do not hand-edit provider mirrors; repository CI owns their generation.
9. For cross-repository coordination, follow `coordinate-repositories` for bounded discovery, isolated-worktree safety, validation, and pull-request state handling. When the user authorizes persistent propagation, carry only canonical `.agents` artifacts and, when bootstrapping a missing agent system, the minimum agent-synchronization implementation, registry, runtime-version, or workflow files it requires. Exclude application code, package source, dependency manifests, tests, runtime configuration, provider outputs, unrelated in-progress work, and manually copied mirrors. Before deciding to reuse an existing pull request, query its current state: a merged pull request is treated as no pull request, so create a new branch and focused pull request. Reuse only an open pull request for the same active branch and task scope. Title the pull request as a synchronization of agent files (for example, `chore: sync agent files`); do not frame consumer changes as modernizing or changing the synchronization system.
10. Report the repositories updated, skipped, or blocked; the requested delta applied; target violations, feasibility judgments, recommendations, and user-selected resolutions; validation results; and every created pull-request link.

## Guardrails

- Preserve dirty worktrees and unrelated changes.
- Never change application code, package source, dependency manifests, tests, runtime configuration, or repository behavior during propagation. Report noncompliance and recommend a separate focused follow-up instead.
- Never reuse, alter, or clean a non-default working branch to perform propagation. Keep the original checkout intact and isolate the carry-over of canonical agent-system work.
- Treat the fetched remote default branch as authoritative for discovery and applicability; a stale or non-default local checkout must never exclude a repository.
- Never exclude a repository from discovery or applicability merely because it has no `.agents` directory or Agent Sync workflow; bootstrap applicable repositories instead.
- Every applicable repository must leave the propagation with a working Agent Sync system; add the minimum canonical bootstrap when it did not already have one.
- Create a missing selected skill when the user explicitly names it or when it is recursively selected as a dependency. Add every canonical rule whose behavior applies to the target, whether or not the user named the rule; do not add inapplicable domain or framework guidance.
- Keep every propagated rule byte-identical to its canonical source. Never tailor rule text per repository.
- Never resolve incompatible canonical, consumer, or target-specific guidance without presenting it to the user and receiving an explicit choice.
- Never treat existing repository noncompliance as evidence that an applicable rule should be tailored or omitted; surface the violation and remediation feasibility to the user.
- Author and replicate canonical `.agents` artifacts; provider-specific outputs must be generated only by the repository synchronization system when it is in scope.
- Treat locally generated provider outputs as disposable test artifacts and leave their publication to CI.
- Keep replicated code examples and reusable instructions repository-neutral; retain domain-specific material only where it is relevant to that target.
- Replace known older generic guidance with its newer canonical wording only when no incompatibility exists.
- Canonical convergence remains the goal, but user approval is required before incorporating consumer guidance or resolving conflicting contracts.
- Do not turn textual similarity or difference into authority; surface semantic incompatibilities for the user to resolve.
- Never propagate secrets, absolute machine paths, generated mirrors, or repository-specific operational details to unrelated repositories.
